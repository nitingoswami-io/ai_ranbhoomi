# pipeline-delivery

Stage 4 of the content pipeline. Takes a rendered bundle in, pushes each piece to its target, records what happened in a local SQLite ledger so re-runs are idempotent.

**Today: apple-notes only.** Delivers via the notes-bridge HTTP endpoint on `localhost:48213` — the same wire protocol the apple-notes MCP server uses internally. No Docker MCP dependency.

## Install

```bash
cd pipeline/delivery
uv sync --extra dev
```

## Run

```bash
# End-to-end from the writer:
python -m writer -i trending.json \
  | python -m renderer -t apple-notes --apple-notes-folder "Daily Brief" \
  | NOTES_BRIDGE_SECRET=$(cat ../mcp_server/apple-notes/bridge/.secret) \
    python -m delivery

# From a saved bundle:
uv run python -m delivery -i apple-notes-bundle.json -o report.json

# Dry-run — no bridge call, no ledger write:
uv run python -m delivery -i apple-notes-bundle.json --dry-run
```

## Idempotency

Every delivery attempt writes `(run_id, topic_id, target) → status, external_id` into `./data/delivery.db` (override with `--ledger` or `DELIVERY_LEDGER`). Re-running the same bundle finds the existing `delivered` row and skips — nothing hits Apple Notes twice for the same `(run_id, topic_id)`.

This is scoped to same-bundle re-delivery. It does **not** replace `trend-radar.mark_covered` — that's the ledger the *novelty gate* consults on future days to decide whether to re-surface a topic at all. Both matter; they answer different questions.

## Configuration

| Env / flag | Default | Purpose |
|---|---|---|
| `NOTES_BRIDGE_URL` / `--bridge-url` | `http://localhost:48213` | Bridge base URL. |
| `NOTES_BRIDGE_SECRET` / `--bridge-secret` | (unset) | Shared secret. The bridge rejects unauthenticated calls with 401 unless its own `NOTES_BRIDGE_SECRET` is also empty. |
| `DELIVERY_LEDGER` / `--ledger` | `./data/delivery.db` | SQLite ledger path. |
| `--dry-run` | off | Skip bridge and ledger; emit a plausible report. |

The bridge's secret is generated by the bridge installer and stored at `mcp_server/apple-notes/bridge/.secret` (gitignored). Read it into `NOTES_BRIDGE_SECRET` in your shell — do not check it in.

## Output

`DeliveryReport` JSON — one `DeliveryRecord` per piece attempted:

- `status`: `delivered` / `skipped` / `failed` / `dry-run`
- `external_id`: the apple-notes note id when delivered (usable to `get_note`/`update_note` later)
- `reason` / `meta.error`: filled on `skipped` / `failed` to explain why
- Exit code `1` if any piece `failed`, else `0`

Delivery never raises on a single piece's failure — partial success is captured in the report and the CLI's stderr summary.

## Tests

```bash
uv run pytest
```

Covers model parsing, ledger read/upsert, dry-run, happy-path delivery against a mocked bridge (via `respx`), idempotent re-delivery, and bridge failure handling.

## What's next

- **Notion target.** Add `notion_client.py` (Notion API token, `POST /pages`) and dispatch on `bundle.target` in the CLI. The `AppleNotesBundleIn` mirror pattern extends to `NotionBundleIn`.
- **`mark_covered` loop-close.** After each successful delivery, call `trend-radar.mark_covered(topic_id=..., post_url=...)`. Two ways to wire it: run `trend-radar` as a subprocess, or open its SQLite ledger directly (path in trend-radar's config). Subprocess is safer.
- **Retries + backoff.** The bridge is local; failures are almost always LaunchAgent state, not transient network. If Notion delivery lands, retry-with-jitter belongs there, not here.
- **Health probe on start.** `client.health()` exists — CLI could call it before iterating and fail loud if the bridge is down.
